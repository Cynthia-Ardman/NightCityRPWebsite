---
name: Portal vitest fragile mocks
description: ncrp-portal component tests with manual api-client-react mocks — how they break after a render-tree refactor and the two fixes that actually work.
---
Several ncrp-portal component tests (EditCharacterDialog.test, CharacterDetail.test, CyberwareEditor via those pages) mock `@workspace/api-client-react` with a manual `vi.mock` factory that enumerates only a subset of hooks. A refactor that grows the eagerly-rendered subtree (e.g. adding inline cyberware editing, or pulling in CatalogRequestSection/CharacterPicker/StaffGrantSections) makes the component call hooks the factory omits, throwing `[vitest] No "<hook>" export is defined`. Add the missing hooks to the factory (enumerate the new subtree with `rg -oN 'use[A-Z][A-Za-z]+|get[A-Z][A-Za-z]+QueryKey'`).

**Two non-obvious failure modes after a Tabs/Accordion/Dialog refactor:**
- **Radix presence loop** — Radix Tabs/Accordion/Dialog mount content via `@radix-ui/react-presence`, whose ref-callback `setState` throws "Maximum update depth exceeded" under jsdom. Fix: flat-mock `@/components/ui/tabs`, `@/components/ui/accordion`, AND `@/components/ui/dialog` to plain `<div>` containers (Dialog gated on `open`). This is the only reliable fix; adding hook mocks alone won't stop it. Tradeoff: loses tab-selection / unmount / focus-trap fidelity, but keeps payload/gating assertions.
- **Identity-dependent hydration loop (a real hang, not a thrown error)** — a `useEffect` whose deps include a query's array (e.g. EditCharacterDialog's cyberware effect on `inventory`/`cyberCatalog`) and which writes derived rows back to state will re-fire forever if the mock returns a **fresh `[]` every render** (React bails only on `Object.is`; `[] !== []`). Symptom: vitest prints "RUN" then hangs with no output (React's depth guard doesn't trip). Fix: return a **stable reference** from those hook mocks (one shared `{ data: [], isLoading: false }`), not `() => ({ data: [] })`.

**Why:** the real generated client exports exist and real React Query preserves data identity via structural sharing, so both modes are mock-realism artifacts, not product bugs.

**How to apply:** when the `test` workflow fails after a portal refactor, first confirm via `git --no-optional-locks status --porcelain` whether the failing files are even in your diff. Pre-existing, out-of-scope failures in unrelated areas (mission-board tabs, breach minigame, sheet decide-staging) reproduce at HEAD and have older `git log -1 -- <file>` commits — treat as pre-existing and skip validation with that reason rather than chasing them.
